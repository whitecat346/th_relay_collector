# 实测语料规律与反模式

> 在 4 个真实 B站 接力话题上实测得到的事实与踩过的坑。
> **目的：下次会话不要重新推导，也不要重试已经证明失败的做法。**
> （原计划写入 Hindsight 知识库，但该服务需要 API key、当前未配置（401），故固化进仓库文档。）

## 一、B站 话题 API（免登录可用）

| 端点 | 用途 | 关键事实 |
|---|---|---|
| `GET api.bilibili.com/x/topic/web/details/top?topic_id=` | 活动身份 | 免登录 `code=0`；`data.top_details.topic_item` 含 `name/description/dynamics/discuss/view`。**`dynamics` 是官方声称的动态总数，可用于完整性断言** |
| `GET api.bilibili.com/x/topic/web/details/cards?topic_id=&sort_by=3&page_size=20&offset=` | 卡片列表 | 免登录 `code=0`；`topic_card_list.items[]` + `offset` + `has_more` |

### 不要重试的失败做法

- ❌ **`x/topic/web/feed`、`rcmd/feed`、`pub/list`、`topic/dynamics`、`topic/list`、`feed/index`、`details/desc`、`details/item`、`pub/detail`** —— 实测全部 **404**。
- ❌ **`x/opus/detail`、`x/dynamic/feed/detail`（含 `platform`/`features` 等变体）** —— 实测全部 **404**。逐棒详情**没有可用 API**。
- ❌ **`page_size=50/100`** —— 服务端**强制钳制为 20**。
- ❌ **`page_num=2` 翻页** —— 无效，**必须用返回的 `offset` 游标**。
- ❌ **不传 `sort_by`** —— 默认 `sort_by=2` 是**热门**，按时间排序的语义会失效。必须显式 `sort_by=3`（最新）。
- ❌ **找 `window.__INITIAL_STATE__` / `module_dynamic` 等 JSON 注入** —— 实测出现次数为 **0**。话题页是渲染后 DOM。
- ❌ **依赖 mhtml 快照作为数据源** —— 保存的话题页只有**首屏**（实测一个 30 棒的活动只装到 4 条接力正文）。mhtml 只能当**解析器回归夹具**。

### 卡片数据结构

- `topic_card_list.items[]` 每项的键名是运行时的：`dynamic_card_item` / `video_card_item` / …，**必须以 `_card_item` 后缀匹配**，不能硬编码。
- 卡片内：`id_str`（→ `bilibili.com/opus/<id_str>`）、`type`（`DYNAMIC_TYPE_DRAW/AV/ARTICLE/FORWARD/WORD`）、
  `modules.module_author`（`mid` / `name` / `pub_ts` / `pub_time` 粗标签）、`modules.module_dynamic.desc.text`、`modules.module_dynamic.major`（保留原始 JSON）。
- **正文位置因卡片类型而异，必须多字段合并**：
  - `DYNAMIC_TYPE_DRAW` → `desc.text`
  - `DYNAMIC_TYPE_AV` → **`major.archive.desc`**，且 `major.archive.title` 常带棒次（如 `【…24h·16：00】`）
  - `DYNAMIC_TYPE_ARTICLE` → **`major.article.desc`**
  - 早期只读 `desc.text` 的探针误判"11/34 条缺正文"；多字段合并后**覆盖 34/34**。
- ⚠ **必须排除噪声字段**：`duration_text`（值如 `"01:58"`）会被标题时间正则误当成"1:58 棒"，造成棒号重复。同类噪声：`bvid/aid/media_type/badge.*/stat/label/cover/face`。

## 二、四个话题的格式差异（过拟合的直接证据）

| topic_id | 活动 | 卡片数 | 格式 | 结果 |
|---|---|---|---|---|
| `1343535` | 「百变因幡帝」10.1帝之日创作接力 | 34（=dynamics，断言1通过） | `第27棒 \| 20:30 \| @名字` | 有棒号 29/30；缺第29棒（正文只写 `23:00点棒`） |
| `1343333` | 10月6日绵月丰姬&绵月依姬接力 | 44（dynamics=45，差 -1） | 多行式 `第32棒 23:00` + 总结专栏（**只有宣图，无名册**） | 有棒号 30/33；缺 12/17/25 —— **前一条没把作者 @ 出来** |
| `1348289` | 凤栖白泽庭竹林组24h | 36（=36） | **完全没有"第N棒"**；逐棒只有 `上一棒@A/下一棒@B`；有**主办总结名册** | 名册反演后 29/30；缺第26棒（名册本身未收录） |
| `1101507` | 中秋永远组24h | 88（dynamics=93，差 -5） | `第N棒`/中文数字/`作者：X（某代发）` 混用；**一根棒发两条动态** | 有棒号 54/49，棒号成对重复 18 个 |

**结论：格式无法靠"一套正则"覆盖，但可以靠 4 类信号**：① `第N棒`（阿拉伯/中文数字）② 时段（`HH:MM |@名`、`HH:MM点棒`、标题 `【…·16：00】`）③ 上下棒 at 链 ④ **话题标签** `#…活动名…#`（归属判定的最强信号）。

## 三、总结名册反演（`ai_guild.md` 的"收集方法优先级 1"）★最高价值

实测 `topic 1348289` 的逐棒正文**既无棒号也无时段**，单卡不可能反演棒号。
但话题页里有一条**主办方的总结动态**：

```
▶前言◀ …本届活动收获了24个整点棒、2个特殊棒、7个应援棒…
▶正文◀
0:00 |@御宫樱寻喵
https://www.bilibili.com/opus/1251670295345889287?spm_id_from=...
1:00 |@简遗w
https://www.bilibili.com/opus/1251685757239689233
5:20特殊棒 |@鴉CORVUS
...
```

**一次请求即可拿到「时段 → 创作者 → 作品链接」的直接映射。**

### 三级匹配（`ArtifactValidator.AssignBarNumbersFromRoster`）

1. **名册作品链接里的 opus id == 卡片 `id_str`** —— 最可靠
2. **创作者昵称唯一命中** —— 名册里同名多个时必须拒绝匹配
3. **时段唯一命中** —— 如视频标题里的 `16：00`

- ⚠ **必须有"槽位唯一认领"**（`used` 集合）。否则同人多帖会抢到名册同一格，产生重复编号（实测 `彩虹面包屑`/`汐骨w` 都拿到第12棒）。
- ⚠ **名册卡本身不是一根棒**。若按普通卡片解析，它会被当成"0:00 那一根"，导致后续棒号**整体 +1**。必须识别并排除（`ParsedBar.IsSummary`）。
- 名册卡识别两条判据：① 命中特征词（圆满结束/感谢各位/活动平台…）且能抽出 ≥4 个棒位；② **正文里罗列 ≥6 个不同棒号**（实测 `1101507` 的总结卡没有任何特征词，只靠棒号密度才认出来）。

## 四、代发判定启发式（不要硬编码主催 mid）★

实测真实形态：

- `上一棒：わふもるり（@沐南沐南沐南 代发）` —— 指**上一棒**由沐南代发，**不是本条**
- `第18棒 19:00 @C1cada_3301 （咖方代发）` —— **本条**由咖方代发
- `本作为代发，画师：R48` —— 明示代发但没写 @
- `第25棒 19:30 @texas_quality`，发布者却是 `texas-engineer` —— **同一人改名，不是代发**

### 已踩过的坑

- ❌ 把"卡片 n 的下一棒代发"记到卡片 n 头上 → **22/34 条被误标代发**。
  修正：代发只认**紧跟上一棒/下一棒人名之后**的括号标注（`PrevProxyRegex`/`NextProxyRegex`）。
- ❌ 把 `who ≠ poster` 一律当代发 → 把"改名"误判成代发。
  修正：**数据驱动的"代发型账号"判定** —— 同一账号有 ≥2 次"正文标注创作者 ≠ 自己"才算代发号
  （实测 `沐南沐南沐南 mid=351852362` 有 12 次、`鴉CORVUS` 多次；`texas-engineer` 只 1 次，故不是）。
- 非代发型账号：`ResolvedAuthor` 一律取**发布者**（`CreatorOf` 也应以 `ResolvedAuthor` 优先），否则 at 链复核会因"改名"误报不一致。

## 五、正则踩坑清单（每条都有实测反例）

| 坑 | 反例 | 修正 |
|---|---|---|
| `who` 字符类漏掉 `\n` | `0:00 \|@御宫樱寻喵\nhttps://...` 跨行匹配后被"跨行守卫"整体拒掉 → **36 张卡片一条都没解析出时段** | who 里**必须排除 `\n`**；单行匹配用独立正则 |
| `\s*` 吃掉分隔符 | `【凤栖白泽庭竹林组24h·16：00】` 里 `24` 被当成 24:00，且 `h` 后无 `】` 导致整体失败 | 时间必须**紧跟分隔符**：`(?<sep>[ ·\-—–_\|｜:：])(?<h>…)` |
| 只认阿拉伯数字 | `第六棒 4：30 @syuugen` 被整条漏掉 → 误报"缺第6棒" | 中文数字归一化（`TextNormalizer.ChineseToInt`，支持 十五/二十/三十四） |
| 棒号后必须有 `@` | `第18棒 19:00 作者：条（咖方代发）`、`第一棒0:00可燃冰块` | who 前用负向回顾排除 `感谢/鸣谢/来自/画师/作者/由/协力/帮忙`；再补 `作者：X` 与裸名字兜底 |
| 话题标签取"最频繁的" | `1343535` 取到 `#因幡帝#`（10/34），而完整话题名覆盖 33/34 | **覆盖率 ≥40%（分母取"带标签的卡片数"）+ 与话题名最大公共子串** |
| 用 `dynamics` 当棒号上限 | `1343535` dynamics=34 而最高棒号=30 → 误报"缺第31~34棒" | 上限用**实际最高棒号**；`dynamics` 与卡片数的差额只作信息性警告 |
| 时段偏差当硬失败 | `第18棒 14:30` 实际发布在 17:42（+193 分钟）——发布延迟是正常的 | 偏差 >120 分钟**只警告**，进待确认清单 |
| 无名册时按时段排序赋号 | 会把无关投稿也编号 | 有名册才反演；无名册只报"需人工确认棒号" |

## 六、既有归档的历史债

- **编码**：22 个 CSV 原本是 21 个 UTF-8-with-BOM + 1 个 GBK（`2025_红龙组24h/data.csv`）。**已在 M6 统一为 UTF-8+BOM**。
- **表头**：22/22 个文件的第 4、6 列**都叫「地址」**（`棒数,时间,作者,地址,类型,地址`）。**按用户决定沿用不改**——语义上第 4 列=作者空间链接、第 6 列=作品链接。`legacy/csv_md.py` 按**列序**读取，不受列名影响。
- **类型词表**：曾有 28 种自由文本（插画 436 / 文章 78 / 视频 42 / 插图 39 / 图片 29 / MMD / 漫画 / 音乐 / COS / 手书 / 照片 / 美食 / 视觉小说 / fumo / 以撒MOD / 玩偶 / 404 / 地图画 / 摄影 / 模型 / 教程 / 绘画 / 演奏 / 歌曲…）。**已在 M6 归一化 插图/图片/绘画 → 插画**（种类 28→25，插画 436→505，语义零变更）。
- ⚠ **`legacy/csv_md.py` 会对棒号做 `float()`**，遇到 `N/A` 直接抛 `could not convert string to float: 'N/A'`。因此渲染器把**棒数异常的行附加在 CSV 末尾**（而非原位），棒号列写 `N/A`。
- **目录命名规范**：`{年份}_{活动名}_{月-日}`（22 个目录中 21 个合规）。违规例：`2025_红龙组24h`（缺月-日）且内部文件名是 `data.csv` 而非目录名。
- `2025_大妖精_8-8` **只有 csv 没有 md**（历史遗留）。
- 全库 **683 行**、**59 行**含 N/A（作者 2 / 作者链接 40 / 作品链接 20 / 类型 17，可重叠）；棒号已到**第41棒**，所以"24h 整点棒"模型不成立。

## 七、环境必需的知识（否则会白折腾）

- **Schannel TLS 失败**：受限沙箱下 .NET 与 `curl.exe` 报 `SEC_E_NO_CREDENTIALS (0x8009030E) 安全包中没有可用的凭证`，因为无法写 `%APPDATA%\Microsoft\Crypto\*` 生成 TLS 临时凭证。**Python requests 走 OpenSSL 不受影响**。联网命令（采集、`--pipeline`、`dotnet publish`）都需要放开该写入。
- **dotnet CLI home 必须重定向**：`DOTNET_CLI_HOME=<workspace>\relay-tool\.dotnet`，否则 `dotnet new/build` 报无法写 `C:\Users\<用户>\.templateengine`。
- **git 签名**：全局 `commit.gpgsign=true`，但 gpg keybox 无法启动 → 已**仅在本仓库** `git config --local commit.gpgsign false`（未改全局）。
- **NuGet 缓存里没有 Spectre.Console** → TUI 必须零依赖：原生 ANSI（`\u001b[`）+ `Console.ReadKey(intercept:true)`。
- **CJK 宽度**：`"第27棒 | 20:30".Length == 12`，终端显示宽度是 15。`.NET PadRight` 一定错位 → 必须用自建的 `TextWidth`（汉字/全角/emoji 记 2 列）。
- **非交互验收**：沙箱里没有交互 TTY，故所有视图支持 `--plain` 单帧渲染；人工确认视图另有 `--selftest-review` 用**合成按键**驱动状态机——这个自检抓到过两个真 bug（初始光标为 -1 导致按键静默失效；Save 写 PascalCase 而 Load 查 snake_case 导致确认"存了读不回"）。

## 八、产品级设计决策（已与用户确认，不要推翻）

- 交付形态：**.NET 10 TUI**（纯 .NET 单语言，不调 Python）；`legacy/csv_md.py` 原样保留但**不复用**。
- 采集：**纯匿名 API**，不装 Playwright；拿不到的棒由用户**手动保存页面**投喂，或进待确认清单。
- 宣传信息（主催/一宣/二宣/终宣/总结）：**只来自 `work/<id>/meta.yml`**，机器抓取结果绝不直接进产物；meta 不存在时只生成草稿并拒绝渲染。
- 人工确认**只能在 TUI 里做**；`review.jsonl` 是机器格式，Markdown 报告是**只读派生物**。
- 最终 CSV 编码 **UTF-8 with BOM**（Windows 中文区 Excel 双击不乱码）；产物契约严格对齐 `legacy/csv_md.py`（6 列 CSV + 三段式 md：`## 宣传` → `## 整点接力` → `## ex棒`）。
- 两道闸门：① 未人工确认不得产出最终归档（`--allow-unconfirmed` 可显式跳过）② 宣传信息只信 meta。
- 棒数异常（多种方法仍无法确定棒号）：**按用户要求按时间排序**，棒号列写 `N/A`，附加在末尾 —— 这类"很常见"，不算失败。
- 创作者没被正确 @ 出来（B站不渲染 `<a>`）：**归为异常交人工处理**。
- git 仓库**只在 `relay-tool/` 内** `init`，22 个归档目录**不入库、不迁移**；工具路径全 ASCII（防 UNICODE 问题），归档目录保持中文（那是用户的检索入口）。
- 输入有两种模式（`ai_guild.md` 明写"tag URL **或单个接力链接**"）：**话题模式**（`--pipeline`）与**单链接模式**（`--opus`）；两者产出同构的 `review.jsonl`，共用同一套 TUI 与 render。

## 九、单链接模式（接力未建话题）的实测事实

### 页面是客户端渲染的，正文藏在 `__INITIAL_STATE__` 里

| 数据 | 位置 |
|---|---|
| 帖子身份 | `detail.basic` —— `comment_id_str` 是**评论接口的 oid**，`comment_type`（opus 实测 12） |
| 作者 | `detail.modules[MODULE_TYPE_AUTHOR].module_author` —— `name` / `mid` / `pub_ts` |
| 标题 | `detail.modules[MODULE_TYPE_TITLE].module_title.text` |
| **正文** | `detail.modules[MODULE_TYPE_CONTENT].module_content.paragraphs[]`（实测 116 段） |
| 评论 | **不在页面里**，要另调接口 |

### ⚠ 踩坑记录（全部实测验证过）

- ❌ **只读 HTML 可见文本** —— 正文/棒次文字出现次数全是 **0**（页面只有壳）。
- ❌ **读 `module_content.text`** —— 实测为**空**；正文只在 `paragraphs`。
- ❌ **用正则取 `__INITIAL_STATE__`** —— 结尾形式每次不同（`</script>` / `(function` / 直接跟下一个标签），
  正则匹配会随机失败。**必须用括号配平**扫描（`{}` 计数 + 字符串/转义感知）。
- ❌ **以为 @ 是 `TEXT_NODE_TYPE_AT`** —— 实测 `@录谜` 是 **`TEXT_NODE_TYPE_RICH`** 节点：
  类型在 `rich.type = "RICH_TEXT_NODE_TYPE_AT"`、UID 在 **`rich.rid`**、
  **`jump_url` 是空字符串**。漏掉这条 → "下一棒 | @某人" 只拿到 "@"，@ 提及列表为空。
- ✅ 节点类型：`TEXT_NODE_TYPE_WORD`（文字在 `word.words`）、`TEXT_NODE_TYPE_RICH`（见上）、
  `TEXT_NODE_TYPE_EMOTE`（表情）。

### 接口选择（实测对照）

| 端点 | 结果 | 结论 |
|---|---|---|
| `x/v2/reply?oid=<comment_id_str>&type=12&sort=2&ps=20&pn=N` | **200 code=0**，有 `replies[]`（含楼中楼）、`page{num,size,count}`、`top`（置顶） | ✅ 抓评论 |
| `x/v2/reply/wbi/main` | **-403 访问权限不足** | ❌ 不要用 |
| `x/polymer/web-dynamic/v1/detail?id=<opus_id>` | **200 code=0**，`data.item` 有 id_str/type/module_author/major | ⚠ 只能补元数据 |
| `x/space/arc/search` | 412（风控） | ❌ |
| `x/space/wbi/arc/search` | **-352**（需要 WBI 签名） | ❌ 未实现签名前不可用 |
| `x/space/opus/list`、`x/space/opus/space` | 404 | ❌ |
| `x/opus/detail`、`x/opus/feed/detail` | 404 | ❌ |

**⚠ `x/polymer/web-dynamic/v1/detail` 对 DRAW 型帖子的 `desc.text` 是 `null`、
`rich_text_nodes` 为空数组、`major.draw` 只有图片 URL —— 正文完全拿不到。**
所以单链接模式**必须抓 HTML 的 paragraphs**，JSON 接口只能作元数据交叉校验。

### 链路遍历的现实

- 正文里的 hashtag 是 `RICH` 节点，`jump_url` 指向 **search.bilibili.com**（实测该 URL 还 404），**不是** opus 链接。
- 实测 `opus/1254218608972660737` 正文为
  `第27棒 | 20:30 | @寒雨笙歌hy / 上一棒 | @录谜 / 下一棒 | @试作型拾九`，
  **@ 只有 UID、没有指向那条动态的链接**。
- 结论：**只能顺"链接"走，不能顺"名字"走**。只 @ 名字时无法自动跟进
  （要自动跟进得靠 `space` 接口 + WBI 签名，尚未实现）；此时工具把 @ 的 UID 记进备注供人工核对。
- 用户给的样例 `opus/959502913797881874` 实测**确实没有棒次标注**：正文是一篇小说（116 段）、
  没有挂话题（`module_topic` 为空）、3 条评论也都无关。工具如实报"链接 0 个"，**不编造**。

### 单链接模式的断言差异（否则会误报）

话题模式的"缺棒"断言从 1 数到最高棒号；单链接模式**只知道链上那几条帖子**，
必须**只检查已知棒位之间的空隙**，否则只给 1 条第27棒时会误报"缺棒 26"。
TUI 里的断言回执（`ReviewView.RecomputeAssertions`）用的也是同一口径。


## 十、风控（v_voucher）与「话题索引」这条免死路 ★

### 症状
搜索接口 `x/web-interface/wbi/search/type` 在同一进程里**只痛快回第一次**，之后返回：

```json
{"code":0,"data":{"v_voucher":"voucher_..."}}
```

`code=0` 但 `data` 里没有 `result` —— **不是「没搜到」，是被挑战了**。
`voucher` 值是随机的，同一台机器用 python 连打 12 次却全部正常，
说明这不是 IP/速率级封禁，而是**请求指纹级别**的挑战。

### 决定性对照实验（同一构建、相隔数秒）

| 组 | 会话 cookie | WBI 签名 | 结果 |
|---|---|---|---|
| A | 注入 buvid3/buvid4（`x/frontend/finger/spi`） | 有 | **v_voucher** |
| B | 无 | 有 | 正常 9 条 |
| C | 注入 buvid | 无 | **v_voucher** |
| D | 无 | 无（只补浏览器头） | 正常 9 条 |

**结论：手工注入 buvid 就是触发器。** 首页（`www.bilibili.com`）已经给 `.bilibili.com`
种过 `buvid3`/`b_nut`，再对 www/api 子域补同名 cookie → Cookie 头里出现**重复的 buvid3**，
这是最异常的指纹。删掉注入后仍会被挑战（因为首页那次 GET 本身也带回了 cookie），
最终定案：**默认完全无 cookie**（`JIELI_SESSION=0` 两跑两正常，`=1` 两跑两 voucher）。

### 最终采用的请求特征（`ChainHttp.cs`）

- UA：真实 Chrome 131 全串；配套 `sec-ch-ua` / `sec-ch-ua-mobile` / `sec-ch-ua-platform`、
  `sec-fetch-dest|mode|site|user`、文档请求加 `Upgrade-Insecure-Requests`。
- **GET 不发 `Origin`**（原来每个请求都带 Origin，浏览器不会这么做）。
- 文档请求（opus 页等）用 `navigate` 头，API 请求用 `cors` 头。
- `/wbi/` 端点自动签名：`wts` + `w_rid = md5(排序后的 query + mixin_key)`，
  参数值先过滤 `!'()*`；`mixin_key` 来自 `x/web-interface/nav` 的 `wbi_img` 文件名，
  按 64 项混淆表重排取前 32 位，缓存 30 分钟。
- 搜索被挑战后**本轮熔断**（`SearchClient.ShortCircuit`），后续步骤直接跳过搜索，
  不再浪费请求去撞墙。

### 话题索引：完全不碰搜索接口

`x/topic/web/details/top?topic_id=` + `x/topic/web/details/cards?topic_id=&sort_by=3&page_size=20`
（offset 游标翻页）匿名可用，每张卡给：

`id_str`（帖 id）、`module_author{mid,name,pub_ts}`、`module_dynamic.desc.text`、
`major{type, archive.bvid, article.id}` —— **视频卡直接给 bvid，专栏卡给 cv 号**。

实测话题 `1349127`（十月八日は博麗霊夢の永遠の巫女就任日）：**46 张卡 / 33 个作者，零搜索请求**，
一次 `--link` 就能铺出 13:30→24:00 共 18 棒（含 4 个视频棒）。

### 代发棒只能靠「正文点名」

同一场里 17:00 那棒是**龙胆紫苑代发**，正文写 `17:00 @茶猫祈祷中`，
作者是代发账号 —— 按作者名/uid 永远找不到。解法是 `TopicIndex.FindByMention(name)`：
在卡面正文里找 `@名字`，唯一作者就当作代发者继续走，`Why` 里写明
「话题卡片正文点名「X」（发布者 Y，可能是代发）」。

### 视频帖的评论 `jump_url` 可能是对象

`content.jump_url{占位符}` 的值**不一定是字符串**，视频/专栏卡占位符是对象：

```
System.InvalidOperationException: The requested operation requires an element of type 'String',
but the target element has type 'Object'.
```

原代码直接 `GetString()` → 实测让视频帖 `BV1iapN6KEtk`（13:30 那棒）整条读取失败、
backward 多出一个假缺口。改为按 `ValueKind` 分派（字符串取原值，对象取 `url`/`jump_url`）。

## 十一、话题时间表补全：`@` 链断开时的兜底 ★（实测于 2026-10-08 灵梦接力）

### 为什么必须做

`--link` 的双向遍历只认「@ 链」。本场 36 棒里，13:30 那棒正文只有一句「第一次真正意义上写灵梦」，
13:00 那棒也不写下一棒 —— **@ 链在 13:00/13:30 之间断开**，纯 @ 遍历只能拿到 18 棒
（13:30→24:00），00:00–13:00 整段丢失。人工 CSV 是 36 棒 + 1 EX。

### 补全流程（`Chain/TopicCompletion.cs`）

1. **翻完所有卡片**：`offset` 游标一直翻到 `has_more=false`。B站按需加载，
   46 张卡分布在 3 页，只看第一页会漏掉大半。
2. **读正文拿「声明时段」**：对未入链的卡读帖内第一处时段。实测能出现的写法（全部已支持）：

   | 写法 | 说明 |
   |---|---|
   | `16：30！` | 全角冒号 + 感叹号，独占一行 |
   | `15：30@反应迟顿` | 全角冒号、时段后紧跟 `@`（无空格无分隔符） |
   | `18:30 阿雯@藏粮阁魔导书` | 时段后是人名，再 `@` 发布账号 |
   | `19:00 作者:@羽衣的皇带鱼` | 时段后接「作者：」 |
   | `10:08 PM @交联纤维素` | 12 小时制 + AM/PM（PM 12→12，其余 +12） |

3. **兜底**：11:00 那棒正文通篇没有钟点 → 用**发布时间四舍五入到半小时**（<15 分→:00、<45→:30、否则下一整点），
   并在 `FieldSources["DeclaredTime"]` 里注明来源，避免静默编造。
4. **提前发布的棒**：15:30 那棒是 **10-07 14:57** 发的（提前一天占位），
   所以补全**不能按发布时间窗口过滤**，只能按声明时段过滤。
5. **同窗多稿**：同一棒常有两张卡（文章版 + 动态版，如 16:30 的「捉迷藏」文章与动态），
   时段相差 < 25 分钟即判为「同一棒的另一稿」，只收一张，其余进告警。
6. **EX / SP**：只有正文行首 `约稿：`/`特典：`、标题含 `约稿：`/`特典：`、或明写「EX棒」才算 EX；
   仅带 `SP` 字样的只提示不自动列入 —— **本场 5 张 SP 帖人工只收了 1 张**（10:08 那张），
   其余是场外应援/插画，硬收会把链搅乱。

### 验收偏差（本场真实踩过的坑）

| 坑 | 现象 | 修法 |
|---|---|---|
| 声明时段容差用了整个窗口 | 22:08 发的 SP 帖自称 18:30，被当成 19:00 那棒收下，真正的 19:00 反而被挤掉 | 声明时段容差收窄到 `min(window, 35)` 分钟 |
| 没有方向一致性判断 | 找「下一棒」时收下自称更早的帖 | `Forward` 时 `declaredDiff < -15` 判冲突、拒收；`Backward` 反之 |
| 搜「鸣谢」误判代发 | 「鸣谢约稿插图作者：@SAM271」让 13:00 蔼石被判成 EX，整棒消失 | 鸣谢/感谢/致谢/约稿/插图行排除，不进创作者归属 |
| 取帖内第一处时段 | 「10:08 PM」帖正文引用了「18:30点棒」，被抢成 18:30 | 有内容的**第一行**行首时段优先于全文任意位置时段 |

### 结果

修完后同一入口一次跑通：**37 节点 = 36 棒 + 1 EX**，棒号/时段与人工 CSV **逐行一致**
（含 4 个视频棒、1 个代发棒、2 个改名账号），请求数 238，零搜索请求。
剩下 2 处缺口都是入口/端点帖「没有识别到上一棒/下一棒 @」的提示，不是真缺棒。

### 交付侧的语义坑（与人工 CSV 逐行比对后修的）

- **反指指向的是「代发账号」**：第 6 棒正文 `5:00 代发：@龙胆紫苑 作者：@Yolandabaka`，
  邻居帖 @ 回来的是龙胆紫苑（大家看到的是他在发），若把反指当第一证据，作者列就会写成代发者。
  最终定序：**帖内自报创作者 > 反指 > 发布者**。
- **类型列要按老词表折**：既有 683 行里「类型」是作品形态（插画/文章/视频/漫画/MMD/音乐…），
  没有「动态」这个词；人工归档把所有图片动态都写成「插画」。渲染时 `动态 → 插画`，
  `文章/视频` 原样保留，更细的类型（音乐/视觉小说/手书）留给 TUI 的 `K` 键。
- **同一棒两张帖要按信息量取舍**：第 22 棒（21:30）@ 链先收到同人视频 `BV1xTHS6MEET`（简介里贴了
  `21:30 @16sanrach 上一棒：@SL8167 下一棒：@上海人偶v`，21:35 发布），而人工归档选的是 16sanrach 的
  动态 `1256826833098244096`。补全阶段遇到「同一时段多张帖」的判定顺序：
  1. 链上那张**没有棒次结构**（无上下棒、正文不提「棒」）→ 换成有结构的；
  2. 链上是**视频**、这里有**动态/文章**，两张都有结构 → 取动态/文章（视频是作品本体）；
  3. 其余情况保留链上那张，另记「重叠」告警。
  替换后来源改 `TopicCards`、置信 0.60，备注写「同一棒有多个帖子，改用带正文的那张」。
  注意别用「简介字数 ≥ 40」当结构判据 —— 同人视频的简介可能 60 多字，却一个字都没提棒次。
- **末棒的 24:00 vs 0:00**：人工 CSV 里末棒写 `0:00`（次日零点），工具写 `24:00`（不歧义）。
  两者指同一时刻；如果要严格复刻人工习惯，渲染前在 TUI 里用 `T` 键改成 `0:00`。

## 十二、同一个话题年年复用：年份污染（实测于 2026-07-26「卡娜日」，入口 `opus/1229219674517930005`）

### 症状

`--link` 跑完，`chain.json` / 报告里的「活动时段」明明写着 2026-07-26，
但链上混进了整批**往年**节点（2024、2025 各十几棒），而且它们都带着合法的「第N棒 8:00」声明时段。
报告「发布时间」列只写 `MM-dd HH:mm`，肉眼根本看不出年份差异 —— 用户是拿渲染出来的 CSV 才发现的。

### 根因（两层）

1. **话题卡片补全没有任何年份/日期限制。** 记忆日话题（`x/topic/web/details/cards?topic_id=1204244`）
   把 2024/2025/2026 三场接力的帖子都放在一起，共 70+ 张卡；补全阶段只要「卡面/正文写了时段」就往
   `dayStart` 上套 → 往年帖子冒充今年。之前为了救「提前一天发布占位」的棒次，
   把 `PubTs` 当天窗口过滤整个删掉了，等于没有任何时间约束。
2. **`MatchVerifier` 只有 ±90 分钟窗口，没有跨天概念。** 往年帖的发布时间与期望时段差 365±1 天，
   但「声明时段」证据照样命中，于是走「结构 + 声明时段」的高置信路径被收下。

### 修法

- `TopicCompletion.CompleteFromTopic`：卡片先分桶，`IsNearRelayDay(card, dayStart)` 为假的一律跳过并计数，
  日志 + 报告告警「话题里有 N 张卡不属于 yyyy-MM-dd 这一场（同话题往年），已跳过」。
  窗口取「活动前一天 0 点 ~ 次日中午」：实测最早提前 1 天发布占位（`10-07 14:57` 发 `10-08 15:30` 那棒），
  更早的、以及结束后一天半以后的，都是别的场次或花絮。
- `MatchVerifier.Verify`：`YearGateDays = 3.0`，`|候选发布时间 - 期望时段| > 3 天` → 直接拒收，
  理由写「超出本场活动范围（同话题往年的帖子）」。两侧都留痕，方便人工核。
- `ChainWriter.WriteReport`：明细表「发布时间」列遇到年份与本场不同的节点，改写 `yyyy-MM-dd HH:mm ⚠非本场年份`。

### 连带修的：棒号重号/跳号

年份修好后暴露出编号问题：`RenumberBySlots` 原来拿「排序后的列表下标 + 1」当推算棒号。
本场 2:00 那一棒话题里根本没有帖（真缺棒），于是后面全体错位，9:00 那棒本该第 10 变成第 9，
和 8:00 的第 9 撞号。改成**锚点式**：先登记所有帖内显式棒号占号位（声明值永不动），
推算时找最近的显式锚点，`guess = anchorBar + round((slot - anchorSlot) / slotStep)`，
`slotStep` 取相邻时段最小差（常规 30/60 分钟）；撞号时顺延到最近空号并写备注。

### 顺带修的：公告帖

同一话题里的「一共24棒+5EX棒，欢迎大家前来围观」「接力名单」「圆满结束，我写个专栏整合」
这些是主办方的公告/汇总帖，带「棒」字但不是任何一棒；以前会被当成 EX 收进报告。
现在卡面文字和读回来的正文都会先过一遍 `IsAnnouncementText`（正则：`一共N棒`/`共N棒`/`N棒+M EX棒`/
`接力名单`/`接力整合`/`圆满结束`），命中就跳过并记一条说明。

### 结果（`--link https://www.bilibili.com/opus/1229219674517930005`）

- 修复前：31 节点，其中 2024/2025 混入 20+ 条；
- 修复后：**28 节点 = 23 棒 + 5 EX**，全部 2026-07-26 当天（EX 数正好等于公告里自称的「5EX棒」），
  棒号 1–24 单调、只在 2:00 那棒留空（话题里确实没有这一棒，报告写进缺口清单）。
- 回归：同构建跑「2026-10-08 灵梦接力」仍是 **37 节点 / 2 缺口**，未受影响。
- 自检：`--selftest-chain` 71 通过 / 0 失败（新增 Q 用例：往年同话题帖必须拒收、提前一天占位仍要收）。

## 十三、时段制接力：正文不写「第N棒」，只写「17:00 @某人」★（实测于 `topic 1349127`）

### 现象

`topic 1349127`（十月八日は博麗霊夢の永遠の巫女就任日）46 张卡，**全篇只有 3 张写了「第N棒」**，
其余都是 `24:00 @拒绝神绮99次`、`23:30 @龙胆紫苑` 这种「时段 + @」。旧话题流程的棒号来源只有
「正文第N棒 + 总结名册」，两者都缺 → 43 条全部「无法归属：正文里找不到棒号」，断言报 1.5、2、3 棒缺失。

### 解法：时段 = 棒位（`Data/SlotGrid.cs`）

1. **活动日** = 卡片发布日期的众数（本场 34 张落在 10-08，1 张落在 10-07）；
2. **每卡取时段**：正文声明的时段优先（`17:00 @茶猫祈祷中` 这种行首写法由新的
   `LineStartTimeAtNameRegex` 提供），否则用**发布时刻**；只认整点/半点（`SlotUnitMinutes=30`），
   次日 0–3 点按 `1440+m` 算；
3. 去重排序后 **第 i 格 = 第 i 棒**（不是「列表下标」，缺一格不会全体错位）；
4. **校准**：拿真写了「第N棒」的卡核对 —— 本场 3/3 对得上，置信度「高」；对不上就整张网格作废、
   逐条标冲突交人工（绝不硬猜）；
5. **排除**（写 `ignored.jsonl`，不产归档行）：同一棒位重复投稿（留 `已声明棒号 > 有声明时段 >
   发布早 > 正文长` 那条）、同一作者的非棒次第二帖（SP/约稿/bgm）、**不在活动日**的预告贴。

### 三个真踩过的坑

- **前一天的预告贴**：10-07 14:57 发帖自称「15：30@反应迟顿」。旧的 `TrySlotOf` 一见声明时段就返回，
  于是凭空多一格 15:30，把后面所有棒号推后一位（16:00 变成第 22 棒而不是 21）。
  修法：声明时段也必须落在活动日（或次日宽限内）。
- **17:27 代发的 17:00 棒差点被当插曲**：「同一作者已有棒位 → 排除」这条规则会把它和龙胆紫苑的
  10:08 宣传帖混为一谈，导致 17:00 整格消失、后续错位。修法：**带「上一棒/下一棒」标注的帖子一定是棒次，
  永不排除**。
- **`17:00 @名字` 拿不到时段**：原有三条时段正则都要求时间与 `@` 之间有 `| ｜ 丨` 分隔，
  这种写法全部落空（于是发布的 17:27 被误当槽位）。新增行首正则作为第 4 条兜底。

### 结果

`--link "https://www.bilibili.com/v/topic/detail?topic_id=1349127"` →
46 张卡 → **34 棒（00:00–24:00）+ 4 条 N/A + 8 条 ignored**，断言 46/46 通过，
无 ✗ 失败；`--review 1349127` 显示「待确认 38　有棒号 34　无缺棒　未归属 4」；
`--render 1349127 --allow-unconfirmed` 出 6 列 CSV（34 棒 + 末尾 4 条 N/A）与三段式 md。
自检：`--selftest-chain` **79 通过 / 0 失败**（新增 R 用例：整点/半小时成格、重复投稿只占一格、前一天预告不进格）。

### 顺带修的渲染 bug

`BuildRows` 把「棒数异常」行同时塞进了 `rows`，而 `BuildCsv`/`BuildMarkdown` 又单独追加了一遍 →
CSV 里 N/A 行写两遍、md 里同时出现「### 第N/A棒」和「## 棒数异常」两处。修法：`rows` 只装整点棒 + EX，
异常行只由第二个参数追加。
